# Price Lens — план и протокол

**План проекта и протокол разговора, из которого он вырос.** Аудит плана вынесен отдельно —
`AUDIT.ru.md`: метод, шкала, 46 находок, что признано исправным, порядок закрытия.

При расхождении силу имеет старшее: **план (часть I) → аудит (`AUDIT.ru.md`) → протокол (часть II).**
Протокол хранит историю: в нём есть рекомендации, которые вы отменили, и это нормально — действующая
версия всегда в плане.

- **Часть I — что строим:** решения, поверхности, данные, потоки, шаги, критерии готовности.
- **Часть II — раунды:** вопрос, альтернатива, рекомендация, ваш ответ, карта развилок.

Открытые вопросы помечены прямо в том разделе плана, который они ломают, — пометкой `Открыто (код)` —
и повторены списком в `AUDIT.ru.md`. Словарь терминов — `CONTEXT.md`. Продолжение после сброса
контекста — `HANDOFF.md`.

# Часть I. План

## 1. Продукт в одном абзаце

Расширение для Chrome и Firefox. Человек выделяет на чужой странице сумму с обозначением валюты —
`$12.50` — и рядом с выделением появляется **попап**: окно с этой же суммой в его собственной валюте.
Если обозначения валюты нет, работает ручной конвертер в **приложении** (то, что в манифесте
`action.default_popup`): два поля и два пикера. Курсы берутся из Frankfurter v2, офлайна нет.

Слова дальше в плане только эти: **попап** — окно с ответом на чужой странице, **приложение** — наша
поверхность с ручным конвертером. «Оверлей» и «окно» в части II и в разделе 13 — старое имя того же
попапа, а не третья сущность.

## 2. Границы MVP

**Входит:** оверлей по выделению, ручной конвертер, настройки (язык, тема, тема оверлея, целевая
валюта, отступ), онбординг из двух экранов, русский и английский, Chrome и Firefox.

**Не входит:** слова-валюты (`100 рублей`), диапазоны (`$5–10`), числа словами (`сто долларов`),
несколько сумм в одном выделении, офлайн-режим, другие браузеры, мобильные браузеры, синхронизация
самих курсов, работа в просмотрщике PDF, на `file://` и внутри iframe (раздел 5) — контент-скрипт там не
запускается, — и публикация в магазинах: MVP ставится себе и друзьям (раздел 5), магазины — следующим
этапом (M6).

## 5. Манифест

Два статических манифеста, один код. Расхождение только в поле `background`: Chrome понимает
`service_worker` и не понимает `scripts`, Firefox — наоборот.

| Поле | Значение |
| --- | --- |
| `manifest_version` | 3 |
| `permissions` | `storage` |
| `host_permissions` | `https://api.frankfurter.dev/*` |
| `content_scripts.matches` | `<all_urls>`, `run_at: document_idle` |
| `content_scripts.all_frames` | не задан — только верхний документ |
| `background` | Chrome: `service_worker`; Firefox: `scripts` |
| `browser_specific_settings.gecko.id` | нужен для Firefox |
| `browser_specific_settings.gecko.data_collection_permissions` | `{ "required": ["none"] }` — Firefox требует ключ у новых расширений; персональных данных нет |
| `web_accessible_resources` | `fonts/roboto-*.woff2` — шрифт окна на чужих страницах; ничего исполняемого |
| `action.default_popup` | `popup.html` — без этого поля приложения просто нет |
| `icons` | PNG 16 / 48 / 128, один набор на оба браузера |
| `version` | строка из точек, до четырёх чисел (`1.0.0`) |
| `name`, `description` | через `__MSG_name__` и `__MSG_description__` |
| `default_locale` | `"en"` — магазин берёт недостающий перевод отсюда |

**Фреймы — вне MVP.** `all_frames` не задан: контент-скрипт живёт только в верхнем документе. Встроенные
блоки — комментарии, встроенные кассы, виджеты магазинов — остаются без окна, и остаются молча: ни
ошибки, ни подсказки, ничего не появляется.

Почему так: попап внутри фрейма физически не может выйти за его границы — рамка фрейма и есть его
вьюпорт, — а у рекламной плашки 300×250 показывать окно у выделения просто негде. Второе: каждый фрейм
это ещё один экземпляр контент-скрипта, а на обычной новостной странице их десяток.

Цена размена записана честно: на сайтах, где цены живут во встроенных блоках, расширение выглядит
работающим наполовину.

Код при этом пишется так, чтобы включение осталось одной строкой в манифесте: контент-скрипт никогда не
обращается к `parent`/`top`, берёт `document` и `window` своего документа, якорь — из
`getBoundingClientRect` того же документа. Допущения «я в верхнем фрейме» в коде нет ни одного.
Возвращаемся сюда первым делом после MVP, вместе со словами-валютами (Р4).

**Публикация в магазинах — после MVP.** Решение пользователя: MVP ставится себе и друзьям,
магазины — следующим этапом. Что это меняет: M5 заканчивается не ревью, а распакованной папкой в Chrome
(режим разработчика) и временным дополнением в Firefox; описаний, скриншотов и политики в MVP нет.

Что при этом пишется **сейчас**, потому что потом дороже: `gecko.id`, `data_collection_permissions` (у новых
расширений Firefox он обязателен; `required: ["none"]` — персональных данных нет), `version`, `default_locale`,
имя и описание через `__MSG_`, иконки. И три обещания, которые обязаны быть правдой с первой строки кода —
они и есть текст будущей политики:

1. наружу уходят только пары валют (`EUR` → `USD`), ни выделенного текста, ни адресов страниц;
2. аналитики нет вовсе;
3. удалённого кода нет: всё в сборке, ни `eval`, ни подгрузки скриптов.

**Инструкция для друзей — вслух, а не в уме.** Chrome ставится распакованной папкой за две минуты. На
релизном Firefox временное дополнение исчезает после перезапуска, а неподписанный `.xpi` не ставится
вовсе: друг выбирает между Developer Edition, переустановкой после каждого перезапуска и подписью AMO
(канал self-distribution — заявка, а не магазин). Это пишется в README при первом же билде: у друга
должна быть причина не решить, что расширение сломано. Первая подпись в AMO — и это начало шага M6.

## 6. Контент-скрипт

Единственная точка входа на чужой странице. Обязанности:

1. Заметить изменение выделения (`selectionchange`) и обработать сразу — дебаунс остаётся только у поля ввода приложения.
2. Взять `selection.toString()`, прогнать через `Exact selection`.
3. Посчитать прямоугольник выделения для позиции и тон страницы для темы.
4. Сходить в фоновый скрипт за курсом (кроме случая «валюта совпала с целевой» — тогда сразу эхо без
   запроса), показать состояния.
5. Нарисовать окно в `ShadowRoot` и убрать его по прокрутке, снятию выделения или клику вне.

Запрос курса идёт через фоновый скрипт, а не напрямую: контент-скрипт живёт в контексте страницы.

**Состояние вкладки — одно место, и оно живёт, пока жива страница.** Решение пользователя: «как глобальное
состояние, которое живёт пока сессия активна, и в него складываем всё нужное». Значит в контент-скрипте
одно состояние, а не переменные по файлам:

| Что в нём | Почему |
| --- | --- |
| снимок настроек (`lang`, `theme`, `overlayTheme`, `targetCurrency`, `gap`) | окну они нужны до первой отрисовки, а чтение из хранилища асинхронное |
| признак «снимок устарел» | гасится событием, снимается перечитыванием |
| текущее выделение: валюта, сумма, прямоугольник | вход и выход одного рендера; окно не хранит их у себя |
| фаза окна: скелетон, число, ошибка | одно поле вместо флагов в разметке |
| номер запроса | ответ с чужим номером отбрасывается: при быстром перевыделении устаревший ответ не перерисует окно чужим числом |

**Чего в нём нет: курса.** Курс живёт в фоновом скрипте и в `storage.session` (раздел 7). Второй кэш во
вкладке означал бы второе место, где курс устаревает, и второе окно свежести — а свежесть уже посчитана
один раз, в фоне. Окно спрашивает `getRate` и печатает ответ; своего числа оно не помнит.

**Перечитывание — по событию, а не по выделению.** Открытие окна в хранилище не ходит вовсе: тема нужна
до первой отрисовки, а `storage.get` асинхронный, поэтому «читать на каждое выделение» дало бы либо
мигание, либо скелетон на самое частое событие в продукте. Снимок гасится `storage.onChanged` (область
`sync`) и перечитывается при следующем открытии окна или при возврате вкладки на экран
(`visibilitychange`: фоновые вкладки браузер замораживает, и событие могло не дойти). Событие при этом не
описание изменения: в Firefox оно приходит со всеми ключами области и бывает без изменения данных (баг
1833153), поэтому мы не разбираем, что поменялось, а просто перечитываем.

**Глобального состояния на все поверхности нет.** Контент-скрипт, попап и страница настроек — три разных
контекста, память у каждого своя; общее — только хранилище. Три поверхности держат три снимка, и это не
ограничение реализации, а факт, о котором лучше узнать сейчас, чем в отладке.

**Позиция и привязка окна вычисляются, а не подгоняются.** Контейнер окна добавляется к
`documentElement`, а не в тело абзаца с выделением: у предка с `transform` координаты `position: fixed`
врут, и единственная защита — держать окно вне чужих transform-контекстов. Координаты берутся из
`getBoundingClientRect` выделения; сторона — сверху, если окно там влезает, иначе снизу; после выбора
стороны окно прижимается к краю экрана с зазором 8 px. Не влезает по высоте даже прижатым — окно не
показывается вовсе: обрезанное окно читается как баг, а не как компромисс.

**Скелетон и число занимают один и тот же размер.** Резерв под две строки (заголовок и деталь ошибки —
тоже две строки) и одинаковые внутренние отступы у обеих фаз: окно не прыгает при смене состояния.

**Клик по окну — наш, и до страницы он не доходит.** `pointerdown` на окне гасится `preventDefault()` и
`stopPropagation()`: иначе страница снимет выделение, правила закрытия сработают раньше `click`, и
кнопка «повторить» — единственный выход из ошибки — умрёт, не нажавшись. Слушатель «клик вне» ставится
на `document` в фазе перехвата, чтобы не зависеть от чужих обработчиков страницы.

## 7. Фоновый скрипт

- `getRate(from, to)` — сначала кэш сессии; если запись свежее окна, отдаёт её; иначе запрос в Frankfurter.
- Пишет в `storage.session` пару, дату курса и время получения.
- Одновременные запросы одной пары схлопываются в один.
- Держит потолок частоты на пару: не больше 3 запросов за 10 секунд и 20 за 10 минут. Запрос сверх
  потолка в сеть не идёт и возвращает «подожди N секунд». Потолок живёт здесь, а не в окне: вкладок и
  окон может быть несколько, и счётчик в окне был бы счётчиком на окно.
- Возвращает не текст, а факт: либо `{ rate }`, либо `{ error: { kind, status? } }`, где `kind` — один из
  шести классов из раздела 11. Тексты живут в словаре окна, а не в фоновом скрипте: иначе один и тот же
  случай пришлось бы описывать дважды — здесь и там.

**Курс не переживает браузер — решение пользователя.** «Оставить только кэш в нашей сессии и всё, сессия
закончилась — новый запрос». Куда он ложится — не вкус, а факт: переменная в фоновом скрипте не годится,
потому что MV3 выгружает скрипт после короткого простоя, и кэш исчез бы вместе с ним — каждая пара
запрашивалась бы заново на каждое выделение. Поэтому кэш лежит в `storage.session`:

- **это память браузера, а не диск**: на диске курса нет нигде;
- **чистится сама**, когда браузер закрыт, а также когда расширение отключено или обновлено;
- 10 МБ на область — при ключе на пару это не тот лимит, о котором надо думать;
- контент-скриптам область по умолчанию не видна, и нам это подходит: курс читает только фон, а вкладка
  получает готовое число (раздел 6).

Цена названа сразу: **после перезапуска браузера первое выделение всегда идёт в сеть**, и офлайн-сценария
у нас больше нет. Раньше вчерашнее число со значком возраста спасало в самолёте; теперь в самолёте человек
увидит «нет подключения» и кнопку. Это тот же размен, что и убранная пометка возраста, и записан он здесь,
а не в отладке.

Побочная выгода: `storage.local` в продукте не используется вовсе. Остаются две области с ясной ролью —
`sync` для настроек, `session` для курса, — и находка С7 (кэш рос на каждую пару и не чистился) теряет
предмет: сессия сама себе граница.

**Сколько живёт запись — шесть часов, и это посчитано, а не выбрано.** Лимит нужен (ваше решение: «вдруг
кто-то будет пользоваться, кто будет неделю ничего не закрывать»), а число — моё, потому что его можно
вывести. Провайдер публикует курс раз в рабочий день, около 16:00 по центральноевропейскому времени, то есть
значение на экране меняется ступенькой, а не плавно. Отсюда два счётчика, между которыми и стоит выбор окна
`W`:

- **запросы:** браузер, который не закрывают, спрашивает одну пару `24 / W` раз в сутки;
- **устаревание:** публикация попадает внутрь окна с вероятностью `W / 24`, и, если попала, человек в
  среднем половину окна смотрит на предыдущее число. За сутки таких часов набегает `W² / 48`.

| Окно `W` | Запросов на пару в сутки | Часов в сутках, когда на экране курс старше опубликованного |
| --- | --- | --- |
| 1 ч | 24 | ≈ 0,02 |
| 4 ч | 6 | ≈ 0,3 |
| **6 ч** | **4** | **≈ 0,8** |
| 12 ч | 2 | 3 |
| 24 ч | 1 | 12 |

Экономия запросов линейна, потеря точности квадратична: удлинить окно вдвое — сэкономить один запрос в сутки
и заплатить вдвое большим устареванием. Порог я взял «меньше часа в сутки на старом числе»: `W² / 48 ≤ 1`
даёт `W ≤ 6,9`, ближайшее значение вниз — **6 часов**. Четыре запроса в сутки на пару — шум рядом с потолком
в 20 запросов за 10 минут, поэтому выторговывать у сети точность незачем.

Условие одно и то же на всю запись: `now - fetchedAt < 6 ч`. Внутри сессии и через её край окно работает
одинаково; запись старше окна не отдаётся — идём в сеть, а при неудаче показываем ошибку с кнопкой. Ничего
«старше окна, но покажем» нет: вчерашнего числа в проекте не существует (раздел 7 выше).

Размен на выходных записан: там не публикуется ничего, и все четыре субботних запроса вернут пятничный курс
с той же датой. Восемь одинаковых ответов за выходные — принятая цена; правило «на выходных не спрашивать»
не берём, потому что оно экономит эти восемь запросов и заводит календарь, о котором больше нечего сказать.
Банк публикует курс и не каждый рабочий день: в дни закрытия TARGET его нет тоже (это проверено: «usually
updated at around 16:00 CET every working day, except on TARGET closing days»), а такие дни не совпадают с
субботой — то есть правило по дням недели дало бы половину календаря.

**Обновление идёт по записи, а не пачкой.** Окно у каждой записи своё, поэтому «протухнуть» целиком кэш не
может: протухает конкретная пара. И протухшее не влечёт запроса само по себе: таймера нет, фонового
обновления нет, устаревшая запись просто лежит и никому не мешает — запрос уходит тогда и только тогда,
когда эту пару снова выбрали. Счёт отсюда прямой: три пары за сессию — три запроса; через шесть часов те же
три пары — ещё три, по одному на пару. Никакого «одного запроса на весь кэш» нет и быть не может — у
записей разные `fetchedAt`.

Пачка возможна, и не вопреки запрету деления: `GET /v2/rates?base=USD` отдаёт таблицу «источник один ко
всем», и `USD → EUR` из неё — чтение ячейки, а не частное. Не берём по размену, а не по вкусу: такой запрос
приносит 159 строк вместо одной (постоянная величина на каждый запрос), а экономит один-два запроса за
сессию — величину, которой рядом с потолком в 20 за 10 минут почти нет. Вдобавок запись перестаёт быть
«курсом» и становится «таблицей курсов»: расходятся и ключ `rate:<FROM>:<TO>`, и контракт из одного значения.
Если счёт изменится (например, появится правка «покажи курс для всех валют сразу») — это правка контракта
`RateSource`, ключа и записи, и решать её вам.

**Провайдер спрятан за одним методом — решение пользователя.** «Вдруг её нужно будет поменять»: наружу из
`background/rate.ts` не выходит ничего провайдерского. Контракт целиком:

```ts
interface RateSource {
  readonly name: string;                    // 'frankfurter'
  fetchRate(from: string, to: string, signal: AbortSignal): Promise<RateResult>;
}

type RateResult =
  | { ok: true; rate: string; rateDate: string }  // сколько `to` за один `from`, десятичной строкой
  | { ok: false; kind: ErrorKind; status?: number };
```

Правила, без которых это не абстракция, а переименование:

1. **Адаптер знает всё провайдерское:** адрес, имена полей в JSON, коды ответов и как статус превращается в
   класс ошибки. Снаружи живут только наши шесть классов (раздел 11).
2. **Курс выходит строкой, а не числом.** Адаптер — единственное место, где значение из JSON становится
   десятичной записью (`String(...)`), чтобы дальше его взял `Big`. Так правило из блока про арифметику
   остаётся одним на весь проект.
3. **В адаптере нет ни кэша, ни потолка частоты, ни выдержки, ни разворота пары.** Всем этим владеет
   `rate.ts`; адаптер только спрашивает и отвечает.
4. **Выбор — одна константа** в `rate.ts`: `const source: RateSource = frankfurter;` — плюс файл
   `background/sources/frankfurter.ts`. Второго места, где импортируется провайдер, нет.
5. **Контракт покрывает один вызов**, потому что второго в рантайме нет: `/v2/currencies` не запрашивается
   (раздел 8), список валют лежит в модуле.

**Чего эта абстракция не обещает.** Смена провайдера — это не только другой адрес: у другого может быть
таблица «база → все валюты» вместо одной пары, другая дата курса, другое поведение в выходные и другие
статусы. Всё это адаптер обязан привести к одному контракту; если привести не получится — меняется
контракт, а не только файл. Обещание ограничено: **остальной код не узнает о смене, пока новый провайдер
выразим этими двумя типами.**

Шов не покрывает манифест: адрес провайдера живёт ещё и в `host_permissions` (раздел 5), причём в двух
файлах. Абстракция делает так, что о смене знает **три** места, а не десять: адаптер, константа, манифест.

**Зачем это, кроме «вдруг».** Шов делает шесть классов ошибок тестируемыми без сети: тест подсовывает
фейковый `RateSource`, который бросает, отвечает `404`, отвечает `200` без поля, и проверяет тексты и
кнопки. Без шва такой тест писался бы на моках `fetch` и проверял бы тексты через чужой JSON.

Альтернатива, которую не берём: отдельный интерфейс на каждую сущность (курсы, список валют, названия).
В рантайме из провайдера ничего, кроме курса, не берётся — второй и третий интерфейсы были бы пустыми.

**Провайдер не умеет конвертировать суммы — и это не наша выдумка.** В документации Frankfurter прямо
сказано: «There's no conversion endpoint. Fetch the rate and convert in a few lines of code», а их же
пример на JS делает `amount * d.rate` по `/v2/rate/eur/usd`. Значит, `GET /v2/rate/{from}/{to}` отдаёт
множитель «сколько `to` за один `from`», и умножать приходится самим.

Это не потеря: множитель и нужен. В приложении человек печатает сумму по одной цифре, и результат
пересчитывается на каждом вводе — запрос на каждую клавишу был бы и медленнее, и грубее. С одним
закэшированным курсом пара запрашивается не чаще раза в шесть часов (провайдер сам советует кэшировать), а
пересчёт суммы — умножение на клиенте.

**Пара тождественная — эхо без запроса.** Источник совпал с целевой: `getRate` не вызывается, но окно
показывает ту же сумму. Решение изменено 2026-11-13: молчание читалось как «расширение не работает»,
особенно на своих же ценах. Это не конвертация и не сеть — только форматирование через `Intl`.

**Арифметика денег — `big.js`, и только он.** Решение пользователя: все арифметические действия над
суммами делает библиотека, чтобы не ловить последствия того, как JS считает числа. Отсюда два правила,
которые нельзя нарушать в другом месте кода:

1. **Формула всё равно одна:** `результат = сумма × rate(источник → цель)`, и `getRate` отдаёт уже
   нормированный множитель, а не сырой ответ провайдера. Деления нет нигде.
2. **Своей арифметики нет.** Ни `a * b / 100`, ни `Math.round` для денег: всё это живёт только внутри
   `shared/money.ts`, и внутри этой функции стоит `Big`.

**Как именно это считается.** Одна строка, но с тремя условиями, без которых она неверна:

```ts
new Big(amountText).times(new Big(rateText)).toFixed(digitsFromIntl)
```

1. **Сумма входит строкой, а не числом.** Парсер уже отдаёт каноническую запись суммы; в `Big` она
   попадает текстом. `Number` туда не передаётся никогда — это и есть тот двоичный формат, от которого
   мы уходим. Строгость ставится на уровне модуля: `Big.strict = true` заставляет конструктор падать на
   `number`, поэтому нарушить правило незаметно не получится.
2. **Курс тоже входит текстом** — его отдаёт таким адаптер провайдера (раздел 7), таким он и лежит в
   `storage.session`: строкой. То есть смена провайдера не может принести в сумму `number`: граница
   проложена там, где значение только появляется.
3. **Знаков — из `Intl`, а не из своей таблицы.** `digitsFromIntl` — это
   `new Intl.NumberFormat(lang, { style: 'currency', currency }).resolvedOptions().maximumFractionDigits`:
   `2` для доллара, `0` для йены, `3` для динара. Тот же `Intl.NumberFormat` потом и печатает.

Округление — половина вверх, и оно задаётся один раз при загрузке модуля: `Big.RM = Big.roundHalfUp`.
Рядом комментарий: менять эти настройки больше негде. `Big.DP` не участвует — он ограничивает только
деление, а мы не делим.

**Почему `big.js`, а не `dinero.js`.** У денежного типа в этом продукте не за что взяться: сумма не
хранится, не складывается, не сравнивается — она умножается один раз и сразу печатается. Из `dinero.js`
мы брали бы последовательность из трёх вызовов, а его таблицу валют всё равно собирали бы сами.
`big.js` решает ту же задачу одной строкой, весит 6 KB без транзитивных зависимостей и не тащит за
собой модель денег — её роль выполняет `Intl`, который и так печатает. Разбор трёх вариантов — в
`AUDIT.ru.md`, находка С13.

**Цена решения, названная вслух.** Зависимость в бандле и две глобальные настройки конструктора
(`Big.strict`, `Big.RM`), которые обязаны быть выставлены в одном месте. Взамен исчезает класс ошибок,
который не падает и не мигает: плавающий остаток и округление в двух разных местах. Версия пинится
точно, а не по `^`: округление — это поведение, которое не должно меняться без нашего ведома.

## 8. Приложение

Ручной конвертер: поле суммы источника, пикер источника, поле результата, пикер результата. Курс — тот
же `getRate`. Тема — тема расширения. Это оно же — `action.default_popup`, то есть поверхность по кнопке
на панели; попап — не оно.

**Невалидный ввод.** Если поле не разбирается — `12.50-13.00`, буквы, пусто — числа нет, а вместо него
строка, которая называет причину: «это диапазон, а не сумма», «не удалось прочитать число». Своё «невалидное
значение» больше не годится по тому же правилу, что и ошибки курса: сообщение обязано говорить, что именно
не так.

Окно на странице в таких случаях молчит: диапазон в чужих ценах — обычное дело, и сообщение об ошибке там
было бы шумом. Сообщение живёт только там, где человек сам набрал строку.

**Разделители в поле — те же, что на странице.** Разбор идёт по правилу раздела 12.2 и не зависит от
валюты в пикере: `12.50` и `12,50` — обе записи читаются как двенадцать с половиной. Отдельного правила
для поля ввода нет: одно правило на весь продукт, чтобы человеку не приходилось помнить два.

Цена записана: у одинокого разделителя с ровно тремя цифрами после него другой трактовки нет — `1.234`
прочтётся как 1234, потому что три знака после запятой ни у одной валюты с индикатором не бывает
(Р2, раздел 12.2). Единственный свидетель — поле результата, и оно поэтому пересчитывается после короткой паузы
250 мс (дебаунс), а не по кнопке: запрос не уходит на каждую клавишу.

**Пикер валют — требование из разговора.** В любом месте, где выбирается валюта: сверху поиск, под ним
строки; в строке узкий знак валюты, затем буквенный код (`RUB`), затем название (`Российский рубль`).
Раньше здесь было «без названия» — решение отменено по примеру, который принёс пользователь. Сама сумма в
приложении показывается только знаком валюты.

**Поля суммы — два одинаковых столбца.** В обоих полях знак валюты стоит отдельным элементом всегда — и
у источника, и у результата — а подставляется только число. Это решение пользователя 2026-11-13: «пусть
будет также всегда рисоваться валюта снизу, а будет подставляться только сумма». Знак даёт
`Intl.NumberFormat.formatToParts`, число — decimal-форматтер с теми же знаками валюты; локаль передаётся
явно.

Названия берутся из `Intl.DisplayNames(lang, { type: 'currency', style: 'long' })`, а не из словаря: 159
названий на двух языках руками не ведутся, и это ещё один повод не держать свои подписи. Поиск ищет по
коду, по названию на языке интерфейса и по началу обоих.

Порядок строк — по названию на `lang`; сравнение — `Intl.Collator(lang).compare` (раздел 14).
Первые строки — отдельный вопрос (`ANSWER.ru.md`).

**Список валют — свой, один модуль.** `src/shared/currencies.ts`: массив кодов на 159 валют — он *и есть*
список доступных валют. Так исчезает целый класс расхождений: перечень и внешний вид — один источник.
`/v2/currencies` в рантайме не запрашивается.

Границы списка: из 181 записи, которые отдаёт `/v2/currencies` (без `scope=all`), убираются крипта (16),
металлы (`XAU`, `XAG`, `XPT`, `XPD`), `CMD` (учётная единица COMESA) и `XDR` (расчётная единица МВФ) —
22 записи, остаётся 159 валют. `CNH`, `GGP`, `IMP`, `JEP` остаются: они не входят в ISO 4217 по номеру, но
это настоящие деньги.

Знаки руками не ведутся: их даёт `Intl.NumberFormat(...).formatToParts` с `currencyDisplay:
'narrowSymbol'` — `RUB` в английской локали становится `₽`, `USD` — `$`, `BOB` — `Bs`. Если узкого знака
нет (`CHF`), в колонке стоит `¤`, а код рядом говорит, что это за валюта. Поле `symbol` провайдера
игнорируется сознательно: знак должен приходить от того форматтера, который печатает сумму.

Модуль, а не json: импорт на сборке, типизация, ни `fetch`, ни `web_accessible_resources`. Нужен он только
приложению, настройкам и онбордингу — в бандл контент-скрипта не попадает.

**Как список обновляется.** Правкой модуля и релизом; повод — новая валюта у провайдера. Темп виден по
самим данным: `BGN` в списке уже нет (Болгария перешла на евро), `XCG` появилась в 2025 году. Одна-две
правки в год — это цена за то, что пикер не зависит от сети.

**Расхождение с провайдером — два края, оба решены.** Валюта в списке есть, а курса по паре нет: окно
показывает текст ошибки и кнопку повтора, в пикере валюта остаётся — состав списка не должен зависеть от
того, что сегодня ответил провайдер. Валюта выпала из следующей версии списка: сохранённая цель
переводится на `USD` при миграции (раздел 10, `schemaVersion`). Таблицы семантических замен (`BGN → EUR`,
`ANG → XCG`) не будет: одна строка вместо двух таблиц. Цена записана: у болгарина целью окажется доллар,
хотя его валюта теперь евро.

**Флагов нет — решение пользователя 2026-11-13.** Windows не рисует региональные эмодзи: вместо флага
появляются две буквы в рамках, и строка пикера превращается в `US USD`. Рисовать 159 флагов картинками —
отдельный набор SVG и его сопровождение; пользователь разрешил отказаться. Поэтому флаг заменён узким
знаком валюты (`₽`, `$`, `Bs`), а код стоит рядом. Колонка знака фиксированной ширины, строки не
съезжают. `showFlag`, `flagOf` и флаги в окне удалены.

**Пикеры не ждут сети.** Список лежит в модуле: состояния «список загружается» больше нет, от сети
зависит только курс.

**Пара приложения живёт сессию.** Решение пользователя 2026-11-13: выбранные в конвертере «из» и «в»
запоминаются в `storage.session` под ключом `app:pair` и переживают закрытие попапа; после перезапуска
браузера сессия чистится, и пара возвращается к дефолту (цель из настроек и `USD`/`EUR` как источник).
Это тот же срок жизни, что у курса: постоянные переключения при серии расчётов утомляют, а хранить пару
на диске смысла нет.

## 9. Настройки и онбординг

| Экран | Что на нём |
| --- | --- |
| Онбординг, экран 1 | язык → тема → целевая валюта, кнопка «дальше» |
| Онбординг, экран 2 | сцена: `The book costs 14,50 € today.`, подсветка только на `14,50 €`, попап сверху с `16,10 $`, пояснение по языку, ползунок отступа |
| Настройки | те же значения плюс кнопка «как это работает» |

**Дефолт валюты следует языку.** Решение пользователя 2026-11-13: если регион не дал валюту, `ru` даёт
RUB, иначе USD. Пока цель в онбординге не выбрана руками, смена языка меняет и её (`en`/USD ↔ `ru`/RUB);
регионная цель (`KZT`, `EUR`) и ручной выбор не перетираются. В настройках после онбординга язык цель не
меняет: там человек уже настроил её сам.

**Решение пользователя 2026-11-13: это не отдельные страницы.** Настройки и онбординг — два вида того
же окна у тулбара. Шестерёнка открывает настройки прямо в окне, «как пользоваться» — онбординг там же,
стрелка возвращает назад; `settings.html` и `onboarding.html` удалены. Из окна на чужой странице кнопка
«другая валюта» открывает это же окно в режиме настроек маленьким popup-окном (`popup.html?view=settings`).
Первый запуск больше не открывает вкладку: онбординг показывается при первом открытии окна у тулбара.

**Сцена — компонент, а не макет.** На втором экране живёт тот же код попапа, что и на чужой странице, и в
него встроен текст `The book costs 14,50 € today.` Подсветка на `14,50 €` сделана CSS, а не настоящим
выделением: тянуть мышью здесь нечего. Попап в сцене включён постоянно и стоит **всегда сверху** от
текста: это задано в компоненте, а не вычисляется по свободному месту — места на сцене хватает по её
собственному макету. Правило выбора стороны из раздела 6 действует на чужих страницах, не здесь.

**Сцена читает живые настройки.** Отступ и тему попапа она берёт не из константы, а из хранилища, и
перерисовывается на месте: человек двигает ползунок — попап отъезжает; меняет тему — сцена меняет её
вместе с приложением. Макет с нарисованной копией показывал бы настройки, которых человек не видит.

Сцена и попап — один код: сцене передаётся прямоугольник якоря вместо выделения.

**Числа на сцене заданы заранее.** `14,50 €` — источник, `16,10` — результат в долларах; это
правдоподобная пара `EUR → USD` (около 1,1103 на день, когда это писалось). Сеть сцене не нужна: она
одинаково выглядит и в самолёте, и в день аварии у провайдера.

Печатает число тот же `Intl.NumberFormat(lang, { style: 'currency', currency: 'USD' })`, что и везде, а
не строка в разметке. На сцене это значит ровно две строки, и обе заданы языком интерфейса:

| `lang` | Что видно в попапе |
| --- | --- |
| `ru` | `16,10 $` — запятая как десятичный знак, символ после числа, между ними неразрывный пробел (U+00A0) |
| `en` | `$16.10` — символ перед числом, точка как десятичный знак |

Захардкожены ровно два числа — `14.5` и `16.1`. Всё остальное в сцене — общий код продукта: форматтер,
тема, отступ, ширина и позиция попапа. Сцена — визуальный пример: она показывает, как это выглядит и куда
встаёт попап, а не проверяет числа.

Поэтому строку `16,10 $` руками не пишем: в компонент передаётся `16.1` и код `USD`, текст строит
форматтер. Голого `$16,10` на сцене не будет ни в одном языке: форматтер печатает под язык —
по-английски `$16.10`, по-русски `16,10 $`, — и строка, написанная руками, разъехалась бы с ним на
первом же языке.

Исходная фраза при этом остаётся текстом страницы и **не форматируется**: `The book costs 14,50 €
today.` — так её написал бы чужой сайт, и сцена показывает именно это (валюта `€`; запятая здесь
десятичная по счёту цифр — после неё две, раздел 12.2).

Термин для такого числа — `Fixture`: значение, заданное заранее и курсом не являющееся. Помечены им только
числа на сцене; в попапе на чужой странице фикстур нет — там только `getRate`.

**Следствие для целевой валюты.** На сцене показаны доллары, даже если человек выбрал тенге: сцена
показывает механизм, а не проверяет настройку. Отдельной сноски нет — решение пользователя 2026-11-13:
фраза «на странице будет ваша валюта» лишняя.

**Флагов в окне тоже нет.** Решение 2026-11-13 закрыло идею `showFlag`: «если это будет сложно
реализовать, то тогда откажемся от флагов». Окно показывает только результат, знак валюты в строке числа
остаётся частью `Intl`; отдельного флага, настройки и `flagOf` больше нет.

**Доступность — минимум, но настоящий.** Результат в окне — элемент с `role="status"` и
`aria-live="polite"`: окно возникает само и больше ничем о себе не сообщает, поэтому появившееся число
объявляется скринридером. Наши страницы (приложение, настройки, онбординг) проходятся с клавиатуры
целиком, порядок табуляции задаётся разметкой. Контраст текста не ниже 4.5:1 в обеих наших темах и в
обеих темах окна. Этого хватает MVP; полный аудит доступности — после него, вместе с публикацией (M6).

## 10. Данные

`storage.sync` — настройки:

```
onboarded: boolean
schemaVersion: 2
lang: 'ru' | 'en'
theme: 'light' | 'dark'
overlayTheme: 'light' | 'dark' | 'auto'
targetCurrency: string
gap: number            // 0..20, дефолт 7
```

`storage.session` — курс, и только он. Это не настройка и не диск: память браузера, которая чистится сама,
когда браузер закрыт, а также когда расширение отключено или обновлено (раздел 7).

```
rate:<FROM>:<TO>  { value: string, rateDate: string, fetchedAt: number }
app:pair         { from: string, to: string }
```

`app:pair` — последняя пара конвертера. Она живёт в той же сессии, что и курс: закрытие попапа её не
стирает, перезапуск браузера — стирает; после него пара снова собирается из настроек.

`value` — строкой, а не числом: так его отдал адаптер провайдера, и так его возьмёт `Big` без
преобразования (раздел 7). `rateDate` — день, на который курс, а не день, когда мы спросили; интерфейс его
больше не показывает (пометки возраста нет, решение Р5), но в записи он остаётся — это факт о курсе, а не
украшение, и если пометка когда-нибудь вернётся, менять контракт провайдера не придётся.

`fetchedAt` — момент, когда курс спросили, и это единственное поле, которое читается не для числа: по нему
считается окно в шесть часов (раздел 7). Три поля — три роли: `value` для суммы, `rateDate` для факта о
курсе, `fetchedAt` для срока.

**`storage.local` в продукте не используется.** Настройки в `sync`, курс в `session` — две области, у
каждой одна роль. И запись курса не переживает браузер: вчерашнего числа взять неоткуда — это цена, а не
недосмотр (раздел 7).

Правила записи: настройки пишутся по факту изменения, отступ — по отпусканию ползунка или с задержкой
(у `storage.sync` лимит на частоту записи).

Правило чтения одно и живёт в `shared/storage.ts`: каждая поверхность держит свой снимок, а не ходит в
хранилище на каждую отрисовку. Снимок гасится `storage.onChanged` и возвратом вкладки на экран; окно при
открытии не читает ничего (раздел 6). Перед первым рисованием интерфейса своих страниц настройки читаются
один раз: пока не прочитаны, онбординг не показывается.

`onboarded` — единственный признак «онбординг пройден»: проверяется только он, отсутствие флага значит
«не пройден». Частичная запись, очистка `sync` и правка хранилища руками больше ничего не ломают —
раньше онбординг показывался по отсутствию настроек и врал во всех трёх случаях.

Лежит в `sync` сознательно: на второй машине онбординга не будет, человек сразу попадает в настройки.
В списке рисков это было Р6, теперь это решение, а не риск.

**Миграция — одна функция, `migrate(from, to)` в `shared/storage.ts`.** При загрузке снимка: если
`schemaVersion` меньше текущего, запись проходит шаги от старой версии к новой (v1 → v2: сохранённый
дефолтный отступ 4 переезжает на 7). Шаг нулевой —
валидация значений: `lang` ∈ `ru`/`en`, `theme` ∈ `light`/`dark`, `overlayTheme` ∈ `light`/`dark`/`auto`,
`targetCurrency` есть в списке (`isSupported`), `gap` ∈ 0–20. Невалидное значение не чинится догадкой:
целевая валюта, которой больше нет в списке, переводится на `USD` (решение С10), и об этом говорится
на странице настроек, а не молча; прочие поля сбрасываются на дефолт так же громко. После шагов
`schemaVersion` записывается обратно. Версия из будущего читается как есть и не перезаписывается:
расширение откатили на старую версию, и затирать данные новой схемы нельзя.

## 11. Потоки

**Основной.** Выделение → `Exact selection` → тон страницы и прямоугольник → запрос курса → скелетон →
число → закрытие по прокрутке, снятию или клику вне.

**Совпало с целью.** Валюта выделения равна целевой — `Exact selection` проходит, окно показывает ту же
сумму, запроса нет (раздел 7).

**Первый запуск.** `onboarded` нет → онбординг, экран 1 с дефолтами из браузера → экран 2 (сцена) →
`onboarded: true`.

**Повторный запуск.** `onboarded: true` → сразу страница настроек, онбординг не показывается.

**Ошибка — это три факта, а не «что-то пошло не так».** Требование пользователя: сообщения об ошибках
должны быть информативными. Расписанное до реализации, это значит: в окне есть (1) заголовок — что
случилось, одной короткой фразой; (2) деталь — с какой валютой и почему, с кодом ответа, если он был;
(3) действие — кнопка, которая действительно помогает. Обе привычные формулы запрещены: «что-то пошло не
так» не говорит ничего, «попробуйте позже» скрывает, что повтор не поможет.

**Класс определяется по наблюдаемому, а не по догадке.** Порядок проверок один и тот же: `fetch` бросил
исключение → таймер (8 с) → ответ пришёл, смотрим статус (429, 5xx, прочие 4xx) → 2xx, но в теле нет
`rate`. Одна причина — один класс, и текстов ровно столько же, сколько классов.

| Класс | Заголовок | Деталь (для пары `USD → KZT`) | Кнопка |
| --- | --- | --- | --- |
| Нет сети | «Нет подключения» | «Курс USD → KZT не получен: браузер не связался с сервером курсов.» | «повторить» |
| Таймаут 8 с | «Сервер не ответил» | «8 секунд без ответа; курс USD → KZT не получен.» | «повторить» |
| `429` | «Слишком много запросов» | «Сервер ограничил частоту (429). Повтор через 12 с.» | «повторить», со счётчиком |
| `5xx` | «Сервис курсов недоступен» | «Сервер ответил 503 — это на его стороне, не в настройках.» | «повторить» |
| `4xx` кроме `429` | «Курса для этой пары нет» | «Сервер ответил 404 на USD → KZT; повтор не поможет.» | «другая валюта» → настройки |
| `2xx` без числа | «Ответ не разобран» | «В ответе нет поля rate (200). Это наша ошибка.» | «повторить» |

**Кнопка есть только там, где она помогает.** При `4xx` «повторить» бесполезно: провайдер уже сказал, что
такой пары у него нет, и второй запрос вернёт тот же ответ. Вместо неё — кнопка «другая валюта», ведущая на
страницу настроек. Условие без кнопки хуже кнопки, обещающей ничего.

**Код ответа видит человек, а не только консоль.** 404 или 429 — единственный факт в ошибке, который нельзя
пересказать сочувствием; без него сообщение остаётся вежливым и ничего не сообщает. Код пишется в детали,
а не в заголовке: шрифт заголовка — обычный, код — второй строкой.

**Устаревшего кэша больше нет — и это записано как потеря.** Пометка возраста и состояние «старый курс»
ушли вместе с кэшем на диске: курс живёт сессию, и вчерашнее число просто неоткуда взять. Окно от этого
короче на два состояния, а в проекте не остаётся `storage.local`. Плата — та же, что в разделе 7: без
сети после перезапуска браузера человек видит ошибку «нет подключения» с кнопкой, а не вчерашний курс с
пометкой.

**Таймаут — 8 секунд, и считается он в окне.** Ждёт окно, оно и ставит таймер: если время вышло, виноват
не обязательно провайдер (фоновый скрипт мог быть выгружен), но человек видит одно и то же состояние —
«сервер не ответил» и кнопку. Этого достаточно и на случай, когда ответа не будет вообще: канал умер
вместе со скриптом — таймер всё равно срабатывает, и второго таймера не заводится. Повтор отправляет
свежее сообщение, а свежее сообщение поднимает выгруженный скрипт штатно — отдельной механики будилки
нет. До реализации поведение проверяется в живом Chrome: что сообщение будит скрипт и что запрос,
начатый в разбуженном скрипте, либо доходит, либо кончается таймером окна, а не вечным ожиданием.

**Тексты — шаблоны в словаре.** По два ключа на класс (`error.network.title`, `error.network.detail`)
с подстановкой пары и кода; английский повторяет ту же тройку «заголовок — деталь — действие». Предложения
из кусков в коде не собираются: иначе перевод развалится на первом же языке, где порядок слов другой.

**«Повторить» всегда идёт мимо кэша.** Кнопка после ошибки запрашивает сеть заново, а не отдаёт то же
сохранённое значение: иначе она выглядит нажатой и ничего не меняет.

Повтор подчиняется двум правилам, и оба нужны, потому что кнопка — основной выход из ошибки:

1. **Пока запрос идёт, кнопка погашена.** Двойной клик не порождает второй запрос.
2. **После n-й неудачи кнопка гаснет на `min(2ⁿ, 30)` секунд** — 2, 4, 8, 16, 30, 30… — и точное
   значение умножается на случайное из `[0.5, 1)`, то есть выдержка каждый раз разная. Это и есть
   jitter. Одному человеку он не даёт ничего, и выдумывать ему задержку сверх выдержки не надо: смысл
   в другом — после общей аварии у провайдера все клиенты в мире идут одновременно, и разброс
   превращает шквал в ровный поток.

Пока кнопка погашена, на ней идёт счётчик секунд: погасшая кнопка без числа читается как поломка.
Потолок частоты держит фоновый скрипт (раздел 7), а выдержку — окно; счётчик выдержки умирает вместе с
окном, чтобы новое выделение не наследовало чужую неудачу.

**Смена настроек при открытом окне.** Пока настройки меняют, окно может быть открыто: переключение
вкладки его не закрывает — это не прокрутка, не снятие выделения и не клик по странице. Поэтому
`storage.onChanged` по области `sync` при открытом окне срабатывает так:

| Что изменилось | Что делает окно |
| --- | --- |
| Тема попапа | перерисовывается на месте |
| Отступ | переезжает на новое место, без запроса |
| Целевая валюта | **закрывается** |
| Язык | ничего: в окне только число, его печатает `Intl` по новому языку |

Почему валюта закрывает, а не пересчитывает — **решение пользователя**, и формулировка его: «поменял
валюту, выделяй заново или считай в основном приложении». Значит окно на странице — витрина, а не рабочий
инструмент: смена валюты — это работа, и её место в приложении, где для неё есть пикер и поле суммы.
Пересчёт в окне превращал бы витрину в мастерскую, для которой у неё нет ни места, ни вида.

Два довода в пользу того же, менее важных, чем решение: число, которое меняется само, без жеста человека, —
это ложь, которую видно только при возвращении; и пересчёт новой пары тянет запрос в сеть из вкладки, на
которую не смотрят.

**Перезагрузки при этом нет нигде.** Настройки живут не в странице, а в `storage.sync`; после смены цепочка
такая: попап пишет ключ → контент-скрипт получает `storage.onChanged` и гасит снимок → **следующее**
выделение в этой же вкладке читает новую целевую и считает по ней сразу. Закрывается только уже открытое
окно — то, которое отвечало на старый вопрос.

### 12.1 Индикаторы

| Индикатор | Валюта |
| --- | --- |
| `$` | USD |
| `€` | EUR |
| `£` | GBP |
| `¥`, `￥` | по языку страницы: `zh*` → CNY, `ja*` → JPY, иначе CNY |
| `₽` | RUB |
| `USD`, `EUR`, `GBP`, `JPY`, `RUB` | по коду |

**`¥` — это две валюты, и знак решается языком страницы.** Решение пользователя: «дефолт китай». Правило
одно: знак `¥` (и полноширинный `￥`) читается как CNY, если страница объявила `zh*`, как JPY, если `ja*`,
и как CNY во всех остальных случаях — включая страницы без `lang`.

У разбора появляется второй вход, и это записано как цена: парсер получает язык страницы рядом с текстом
выделения, тесты обязаны его передавать. Первый вход по-прежнему один — текст.

**Ошибка никуда не уходит, она меняет сторону.** Раньше врали китайские цены на страницах с `lang="zh"`;
теперь врёт японская цена на странице, которая язык не объявила: `¥1 500` прочитается как юани и покажет
число примерно в двадцать раз меньше. Такой случай в природе есть (англоязычная статья о японских ценах,
страница без `lang`), и он записан здесь, чтобы возвращаться сюда, а не искать баг в парсере. Кодами
`JPY` и `CNY` это работает всегда и без догадок.

**Обозначений может быть несколько — валюта обязана быть одной.** Решение пользователя по Б12. Три правила
и всё:

1. **Все обозначения в выделении указывают на одну валюту** — тогда это одна сумма с повтором: `$12.50 USD`,
   `12,50 € EUR`. Если хоть одно спорит — `$12.50 CAD`, `12.50 USD EUR` — выделение не принимается: выбор
   одного из двух был бы подброшенной монетой, поданной как ответ.
2. **Код считается кодом, только если его не касается буква.** Границы — цифра, пробел, дефис (он всё равно
   вычёркивается нормализацией), конец строки. `USD 12.50`, `12.50USD`, `RUB100`, `USD-12.50` — да;
   `USDT 100`, `12.50 USDX` — нет.
3. **Сумма ровно одна.** Две суммы со своими валютами (`USD 12.50 EUR 13`) и сумма без обозначения (`12.50`) —
   не наш случай.

| Выделение | Окно | Почему |
| --- | --- | --- |
| `$12.50 USD`, `€12.50 EUR` | да | обозначения совпали |
| `usd 12.50` | да | регистр не важен |
| `$12.50 CAD`, `12.50 USD EUR` | нет | обозначения спорят |
| `$12.50 USDT` | нет | `USDT` — чужой тикер, спорит с `$` |
| `USDT 100`, `USDT12.50`, `12.50 USDX` | нет | код продолжен буквой — это не код |
| `BUSD 100` | нет | такого кода у нас нет вовсе |
| `USD 12.50`, `12.50USD`, `RUB100`, `USD-12.50` | да | код на не-буквенной границе |
| `12.50` | нет | числа хватает, обозначения нет |
| `$12.50–13.00`, `$12.50 и $13.00` | нет | это не одна сумма |

**Регистр не важен:** `usd 12.50` — та же сумма, что `USD 12.50`. Строчными коды тоже пишут, а ошибок это
почти не даёт.

**«Недокод» отклоняется, и это шире обычной границы.** `USDT`, `USDC` и подобные начинаются с `USD` и
продолжаются буквой: такой тикер считается чужим и спорит с символом, поэтому `$12.50 USDT` — отказ, а не
«наверное, доллары». Остаётся названная неточность: `$12.50 BUSD` покажет доллары, потому что `BUSD` не
начинается ни с одного нашего кода. Ловля этого случая — уже словарь криптотикеров, а его в MVP нет.

**Правка 2026-11-11 (реализация, помечено для решения).** Этот абзац противоречил строгому §12.3:
`BUSD` — выжившие буквы, а §12.3 требует «весь текст — ровно одна сумма», то есть `$12.50 BUSD` —
**отказ**, не доллары. Реализовано строгое §12.3 (тест в таблице парсера помечает случай). Вернуть
старое поведение — значит научить парсер игнорировать неизвестные буквенные хвосты; это одна строка
классификации, но решать — вам, потому что тогда `цена $12.50` тоже начнёт давать окно.

**Что решилось позже.** `€12.50` когда-то читался как `1250` — по валютной таблице раздела 12.2;
с 2026-11-08 арбитр разделителей — счёт цифр, и эта запись читается как 12,50 (Р2 закрыт, раздел 12.2).

### 12.2 Формат числа

**Арбитр разделителя — счёт цифр, а не валюта** (решение пользователя 2026-11-08, пересмотр раунда 6).
Основание одно: тысячная группа всегда ровно три цифры — в обоих соглашениях, которые нам нужны, —
поэтому форма записи говорит сама за себя, и валюте знать про разделители не нужно. Три строки, в
порядке применения:

1. Есть оба разделителя — десятичный правый.
2. Одинаковых разделителей два и больше — все они тысячные. Это спасает индийскую группировку
   `1,00,000`, где группы по две цифры.
3. Один разделитель — он тысячный, только если за ним ровно три цифры; иначе он десятичный. В записи,
   где тысячи уже сгруппированы пробелом, единственный оставшийся разделитель всегда десятичный — даже
   при трёх цифрах после него.
4. Тысячная трактовка не действует за ведущим нулём: `0.500` — это половина, не пятьсот
   (группировка `0` невозможна; добавлено при реализации 2026-11-11).

| Запись | Читается |
| --- | --- |
| `€12.50`, `$12,50`, `€1.5` | 12,50 / 12,50 / 1,5 — разделитель один, цифр после него не три: десятичный |
| `$1.234`, `€1.234`, `$1,234` | 1234 — один разделитель и ровно три цифры после него: тысячи |
| `1.234,56`, `1,234.56` | 1234,56 — оба разделителя, правый десятичный |
| `1,00,000` | 100000 — повтор одного разделителя: все тысячные |
| `1 234` | 1234 — пробел (любой пробельный символ после шага 0 из 12.3) всегда тысячи |
| `1 234,56`, `1 234.56` | 1234,56 — пробел сгруппировал тысячи, оставшийся разделитель десятичный |
| `1 234.567` | 1234,567 — то же правило: три цифры после разделителя не делают его тысячным |

Четвёртая строка не нужна сегодня, но зарезервирована: у валюты с тремя знаками (`KWD`, `BHD`) `1.234` —
это одна целая двести тридцать четыре тысячных, а правило прочтёт 1234. Индикаторов таких валют в списке
нет (§12.1 даёт 2, 2, 2, 0, 2 знака); если такой индикатор появится, добавится строка «для валюты с
тремя знаками единственный разделитель с тремя цифрами после него — десятичный».

Правило одно на весь продукт: и для текста на странице, и для поля ввода в приложении (раздел 8).
Валюта разбору по-прежнему нужна — сказать, **что** за сумма, — но разделители она больше не решает;
на странице она берётся из индикатора, в приложении — из пикера.

### 12.3 `Exact selection`

**Шаг 0 — пробелы, до всякой регулярки.** Все разновидности пробельного символа — обычный, неразрывный
(U+00A0), узкий неразрывный (U+202F), тонкий (U+2009), таб, перевод строки — приводятся к обычному
пробелу, а любая последовательность пробельных символов схлопывается в один. Основание: банковские и
типографские страницы пишут `1 234 €` узким неразрывным пробелом, и без этого шага такое число
отклоняется; а `selection.toString()` склеивает многострочное выделение переводом строки, из-за чего
`$12.50\n` и `12\n.50` вели бы себя иначе, чем тот же текст с пробелами. После шага 0 пробел в правилах
ниже — всегда ровно один обычный пробел.

Выделение принимается, если после нормализации весь его текст — ровно одна сумма с индикатором. Любой
другой символ делает выделение обычным копированием.

**Нормализация: одна регулярка вместо списка обёрток.** Вычёркиваем всю пунктуацию, кроме точки и запятой, и,
разумеется, кроме самих знаков валют — иначе индикатор не переживёт нормализацию:

```ts
const NOISE = /[^\p{L}\p{N}\s.,$€£¥₽￥]/gu;
const EDGE = /[.,]+$/;
```

Что получается даром: `«`, `»`, `"`, `'`, `(`, `)`, `!`, `?`, `;`, `:`, `…` просто исчезают, и левая
сторона от правой не отличается — перечислять обёртки больше не нужно. Буквы остаются: без них `USD`
перестал бы быть индикатором.

**Отдельное условие для `$12.50.`** — то, чего регулярка сама не умеет: после `NOISE` в конце может
остаться точка или запятая, за которой ничего нет, и она не может быть частью числа. Снимаем хвост по
`EDGE`.

**Тире: прощается или отклоняется — зависит от того, где оно стоит.** Тире — такая же пунктуация, и
вычёркивать его мы будем; но перед этим одна проверка: если в тексте без пробелов цифра стоит вплотную к
тире с обеих сторон — `12.50–13.00`, `12.50 - 13.00`, `1 234 — 1 500` — это диапазон, и выделение
отклоняется целиком. Проверка на «цифра-тире-цифра» после удаления пробелов ловит и диапазон с пробелами.

Всё остальное тире — просто знак: `$12.50-` и `— 12.50 ₽` разбираются как `$12.50` и `12.50 ₽`.

### 12.4 Множители

`тыс.`, `млн`, `K`, `M` умножают число. Множитель и индикатор могут стоять в любом порядке относительно
суммы.

## 13. Тема и тон страницы

Тема расширения — только `light` и `dark`, снимок, снятый на онбординге. Живой связи с системой нет, и
это принято как решение: человек, сменивший системную тему, увидит расширение прежним, пока сам не
поменяет настройку. Поэтому пояснение стоит под **обеими** настройками темы — и рядом с темой
расширения («за системой не следует, поменять — здесь»), и рядом с темой оверлея: непонимание возможно
у обеих.

Тема попапа — своя настройка, и у попапа ровно две темы, обе заданы заранее: светлая и тёмная. Код
не рисует тему на лету, а подставляет готовую.

| Что говорит страница | Попап |
| --- | --- |
| Объявила светлую | светлый |
| Объявила тёмную | тёмный |
| Молчит, но красит: первый непрозрачный `background-color` от `html` к `body` | по яркости фона: темнее 0,5 — тёмный, светлее — светлый |
| Молчит и не красит (фон прозрачный) | тема приложения |

**Как читается объявление.** От начала документа: `color-scheme` на `html`; затем токены классов и
значений атрибутов на `html`, а если он промолчал — на `body`: `dark`, `dark-mode`, `theme-dark`,
`is-dark`, `night`, `light`, `light-mode`, `theme-light`, плюс `data-theme`, `data-bs-theme`,
`data-color-mode` со значением `dark` или `light`. Сравнение — по целому классу или значению, не
подстрокой: `darkroom` и `lightbox` темой не считаются. Побеждает первое найденное объявление.

**Решение пользователя (Б5):** тему попапа решает то, что страница сказала о себе, а не краска под
выделением. Попап следует теме сайта целиком, какой её задумал автор, и не меняет цвет от блока к
блоку.

**Решение пользователя (2026-11-08, закрытие Р8):** «если тема попапа авто, то выбор идёт от цвета
страницы». Когда страница молчит, её цвет читается с самой страницы: берётся первый непрозрачный
`background-color` от `html` к `body`, считается яркость (относительная яркость WCAG); темнее 0,5 —
тёмная тема, светлее — светлая. Нет ни объявления, ни цвета — тема приложения, и это то самое «если
определить нельзя — берём цвет нашего приложения» из раунда 13а.

Граница из Б5 при этом выживает: краска читается только на уровне страницы, но не под выделением —
тёмная карточка на светлой странице окно не перекрашивает. `background-color` предков выделения в
цепочке по-прежнему не участвует: он отвечает на вопрос «что под числом», а не «какая тема у страницы».

Обязательные следствия: фон окна непрозрачный, у окна есть тень и тонкая рамка в 1px.

## 14. Локализация

**В приложении один источник языка — настройка `lang`.** Не «в основном» и не «кроме пикера»: любое место,
которому нужен язык — подписи, названия валют, порядок строк, поиск, числа, склонения, `lang` на `html` —
берёт его оттуда и только оттуда. Язык браузера нужен ровно один раз: при онбординге, чтобы у `lang`
появилось начальное значение. После этого к браузеру за языком не обращается ни одна строка кода.

Исполняется это одной точкой входа: `shared/i18n.ts` держит текущий `lang` и отдаёт его всем, кому он
нужен. Другого источника языка в проекте нет.

`_locales/ru/messages.json` и `_locales/en/messages.json`. Оба словаря импортируются на этапе сборки,
выбор — по нашей настройке. `chrome.i18n.getMessage` не используется именно потому, что он берёт язык
браузера и настройку не видит.

Переводится всё, кроме строки-примера на сцене онбординга: она одна для всех.

**Где правило ломается без ведома автора.** Не на `navigator.language` — на умолчаниях: `localeCompare()`
без аргумента, `new Intl.Collator()`, `new Intl.DisplayNames()`, `new Intl.PluralRules()`,
`toLocaleString()` без локали молча берут язык браузера. Человек с браузером на русском и интерфейсом на
английском получил бы пикер, отсортированный и подписанный не тем языком, каким он его читает; ошибки
при этом нет — есть список не в том порядке. Поэтому локаль передаётся аргументом всегда, а
`localeCompare()` без аргумента в коде не появляется.

Следствие для живых настроек (Б11): смена `lang` — это не замена подписей, а смена сортировки и
поискового индекса. Пикер, открытый в момент смены языка, перестраивается целиком — имена, порядок,
поиск.

**Карточка расширения в магазине — не наша поверхность.** Имя и описание подставляет браузер из
`__MSG_` и `default_locale`, и переводит он их по своему языку. На наши страницы и на пикеры это не
распространяется: там только `lang`.

**Склонения по числу.** Плоский json «ключ → строка» не умеет русских форм по числу — там, где в тексте
число со словом, ключ заводится на каждую форму, а форму выбирает `Intl.PluralRules(нашЯзык)`: для
русского это `one`/`few`/`many`/`other`. Где слово можно не склонять — его нет: счётчик на кнопке
повтора пишет «12 с», а не «12 секунд», и ключей на формы не требует. `PluralRules` — ещё один
конструктор из списка выше, который без локали молча берёт язык браузера; локаль передаётся всегда.

**`lang` на `html` и отсутствующий ключ.** При загрузке каждой нашей страницы
`document.documentElement.lang` выставляется из настройки — до первой отрисовки, чтобы скринридер и
системные проверки читали страницу тем языком, каким она говорит. Отсутствующий ключ не падает и не
подставляет тихо другой язык: в интерфейсе выводится имя ключа (`settings.title`), а проверка на сборке
сравнивает наборы ключей обоих словарей и валит сборку при расхождении — ключ, забытый в одном языке, не
дойдёт до пользователя.

**Ключи в `messages.json` — только ASCII `[A-Za-z0-9_]`.** Это проверка Chrome: ключ с точкой
(`settings.title`) отвергается и расширение не загружается вовсе — проверено установкой распакованной
папки. Поэтому в словарях точки заменены подчёркиваниями (`settings_title`), а в коде остаётся читаемый
`t('settings.title')`: `shared/i18n.ts` переводит точки в подчёркивания при поиске. Тест на сборке
проверяет не только паритет наборов, но и допустимый алфавит ключей.

Два прохода сборки: контент-скрипт в формате `iife` с фиксированным именем файла; остальное — `esm` плюс
html. Манифесты лежат статическими файлами и подставляются в сборку.

**Внешний вид делается под руководством навыка `frontend-design`.** Решение пользователя (2026-11-08):
навык загружается до первой строки UI-кода каждой из четырёх поверхностей и работает как бриф дизайнера —
намеренные палитра, типографика и компоновка, два прохода (план-токены → проверка против шаблонных
решений → код), смелость в одном месте, остальное — тишина. Иерархия при конфликте: правила этого плана
сильнее навыка. Темы (раздел 13), состояния и тексты ошибок (раздел 11), печать чисел (раздел 12),
«в окне только результат» — продукт, и навык их не пересматривает; его вопрос — «как это выглядит», а не
«что это делает».

**Рантайм-зависимость ровно одна — `big.js`.** 6 KB, без транзитивных зависимостей. Версия пинится точно
(не `^`): округление — это поведение, а оно не должно меняться без нашего ведома. Таблицы валют внутри
библиотеки нет вовсе — знаки и число знаков остаются за `Intl`. Остальное — браузерные API.

**Шрифт — Roboto, но не из Google Fonts.** Решение пользователя 2026-11-13: интерфейс на Roboto. Два
woff2 — латиница и кириллица — лежат в проекте, в `public/fonts/`; сборка кладёт их в `fonts/`. Никакого запроса к `fonts.googleapis.com`: это нарушило бы обещание
«наружу уходят только пары валют». На чужих страницах окно подключает тот же файл через
`web_accessible_resources`; если CSP страницы запрещает шрифты, остаётся системный запасной.

**Линт и форматирование — oxc.** Решение пользователя (2026-11-08): ESLint/Prettier не заводятся вовсе;
код проверяет `oxlint`, формат — `oxfmt`. Оговорка записана честно: `oxlint` стабилен, `oxfmt` с февраля
2026 в бете, стабильный релиз ещё не вышел — для проекта из одного рантайм-пакета риск приемлем, а если
бета где-то сломается, откат на Prettier — правка одного dev-зависимости. Оба входят в каркас с первого
тикета: сборка не зелёная, если линт красный.

**Манифесты проверяются сборкой.** Тест на сборке сравнивает оба манифеста по всем ключам, кроме
`background` и `browser_specific_settings`: правка версии или прав, забытая во втором файле, валит
сборку, а не находится в отладке через месяц.

**Тесты — `bun test`, без отдельного рантайма.** Покрываются чистые модули: `parser` — обязательная
таблица 25–40 случаев (суммы, форматы, множители, разновидности пробелов, диапазоны, отказы), `format`,
`tone`, `position` — по своим правилам из плана. Красных тестов парсера или их отсутствия быть не
должно к началу M3: правило разделителей живёт только в тексте, и без таблицы оно развалится молча.

## Раунд 1. Поверхность виджета

**Вопрос.** На какой поверхности живёт виджет?

**Почему это первая развилка.** От неё зависят почти все остальные решения:

- можно ли ходить в сеть за курсами и насколько это критично для работы;
- насколько жёсткий бюджет на размер бандла;
- значит ли «виджет» — «встраивается чужими руками на чужую страницу» или просто
  «компонент нашего собственного приложения».

**Рекомендую:** встраиваемый и независимый от фреймворка. То есть самодостаточный бандл,
который чужая страница подключает одной строкой; виджет сам владеет своим DOM, стилями и
жизненным циклом и ничего не предполагает о фреймворке хоста. Это стандартное прочтение слова
«виджет» и именно тот вариант, где есть настоящие ограничения: изоляция стилей, отсутствие
общих глобальных переменных, непредсказуемый контейнер.

Альтернатива: если это просто страница, которой владеете вы, задача резко упрощается — и я
не хочу проектировать под ограничения, которых нет.

**Ваш ответ.** Браузерное расширение для Chrome и Firefox. Это не бандл, который кто-то
встраивает к себе: расширение само работает на чужих страницах, которые мы не контролируем.
Три поверхности:

- **оверлей** над или под выделенным текстом — основной сценарий;
- **конвертер без выделения** — два поля и выбор валют, для случаев, когда обозначения валюты
  в тексте нет (попап или отдельная страница настроек — уточним);
- **настройки** — валюта по умолчанию, язык, тема.

**Уточнение по bun.** Расширение исполняется в браузере, поэтому bun — не рантайм продукта, а
инструмент разработки: зависимости, сборка, тесты. В рантайме будут браузерные API и обычный
JS. Отсюда следует, что «чем собирать два манифеста из одной кодовой базы» — отдельное
решение, и сборщик bun здесь не единственный и не очевидный претендент. Вынес в карту ниже.

исходная и целевая валюта, валюта по умолчанию, конвертация, курс, оверлей, попап, онбординг.

## Раунд 2. Когда оверлей появляется

**Вопрос.** Оверлей показывается сам на любое выделение, которое удалось разобрать, или только
по запросу — по горячей клавише или кнопке рядом с выделением?

**Почему это следующая развилка.** Это решение задаёт характер продукта и жёстко определяет,
каким должен быть разборщик:

- если оверлей появляется сам, разбор обязан быть точным. Иначе виджет будет выскакивать на
  каждом выделении текста — мешать копировать, закрывать собой чужой интерфейс. Приоритет
  смещается к точности, а не к полноте;
- если по запросу, цена ошибки низкая и разбирать можно смелее: рыхлые форматы, слова вместо
  символов. Но появляется цена обнаружения — человек должен помнить про горячую клавишу.

Есть и вторая сторона: многие сайты сами показывают панель над выделением (Notion, Medium,
Google Docs). Наш оверлей будет с ними толкаться, и это аргумент против самопоявления.

**Рекомендую:** автоматически, но только на «уверенном» разборе. Практически: цифры и символ
валюты идут одним куском (`$12.50`, `12,50 €`), рядом нет других цифр, выделение не внутри
поля ввода; оверлей закрывается по Esc и не всплывает повторно на том же выделении. Рыхлые
случаи (`$5–10`, `5 млн ₽`, `сто долларов`) автоматически не показываем — до них человек
добирается через попап.

Альтернатива, которую стоит взвесить: только по горячей клавише. Тогда разборщик можно
сделать заметно смелее, а продукт перестаёт мешать на чужих страницах.

**Ваш ответ.** Показ автоматический, на 100%, без горячей клавиши — это принципиальная часть
продукта. Триггером считается любая из перечисленных записей суммы:

- `$12.50`, `12,50 €` — символ и число одним куском;
- `$5–10` — диапазон;
- `5 млн ₽` — число с множителем;
- `сто долларов` — число словами.

Дальше из выделения берутся валюта и числа и уходят в запрос.

**Правка 2026-11-08 (П2).** Этот список — первая формулировка триггера, позже суженная: диапазоны
отложены, числа словами убраны, слова-валюты убраны (раунды 3, 4 и 5а). Действующая версия — часть I,
раздел 2: ровно одна сумма с индикатором, цифры и множители.

**Что я обязан сказать.** Мой «уверенный разбор» вы отвергли — это осознанный отход от
очевидного пути. Такому решению место в ADR: будущий читатель кода спросит, почему на чужой
странице оверлей всплывает без всяких гейтов. Я его запишу, но причину вы сформулируете сами —
придумывать обоснование за вас я не буду. Спрошу об этом, когда закроем ветку.

## Раунд 3. Одна сумма или несколько

**Вопрос.** Что показывает оверлей, если в выделении больше одной суммы, и что считать «одной
суммой», когда она записана диапазоном?

**Почему это сейчас.** Вы сказали «подставляются валюта и числа». Но конвертация в нашей модели —
это одна сумма и один курс (см. `CONTEXT.md`). Отсюда три разных случая, которые не сводятся
друг к другу:

1. **Одна сумма.** `$12.50` — всё однозначно.
2. **Диапазон.** `$5–10` — одна запись суммы, но два числа. Показать «5–10 $ → 480–960 ₽»?
   Только нижнюю границу? Обе границы двумя строками? Сегодня диапазон — это *одно*
   срабатывание, потому что человек выделил одну цену, а не дважды нажал.
3. **Несколько разных сумм.** Абзац с тремя ценами или строка таблицы. Это уже не «цена», а
   «текст, в котором есть цены» — и это самый частый вид выделения на практике: люди выделяют
   фразу, чтобы скопировать её целиком.

**Рекомендую:** срабатывать только на выделении ровно одной записи суммы; диапазон считать одной
записью и показывать результатом-диапазоном на одном курсе. Если в выделении больше одной
записи суммы — оверлей не показывать вообще.

Причина: это последний оставшийся гейт, и он не отменяет ваше «100% автоматически». Вы ничего
не нажимаете — вы просто не получаете оверлей, когда выделили текст, а не цену. Без такого
гейта выделение абзаца на новостном сайте будет вызывать всплывашку с курсом доллара, и это
будет ощущаться как поломка, а не как фича.

Альтернативы: показывать первую сумму; показывать все списком. Вторая превращает оверлей в
панель и требует совсем другого интерфейса.

**Ваш ответ.** MVP: ровно одна сумма. Диапазон — не сейчас: если понадобится, придёт отдельной
фичей.

**Следствие, которое надо проговорить.** Два раунда назад `$5–10` был у вас в списке триггеров.
Теперь он из списка выпадает: на выделении `$5–10` оверлей не появится, потому что в выделении
две суммы. Это не регресс, а следствие выбранного среза — фиксирую, чтобы потом это не сочли
багом.

**Уточнение термина.** Убрал `Range` из `CONTEXT.md`. Глоссарий описывает то, что продукт
моделирует, а не то, что он когда-нибудь будет моделировать — иначе читатель решит, что
диапазоны поддерживаются. Термин вернётся вместе с фичей.

**Модель одного срабатывания** (закрепляю формулировку): оверлей появляется тогда и только
тогда, когда выделение содержит ровно одну запись суммы.

## Раунд 4. Числа словами

**Вопрос.** Входят ли в MVP числа, записанные словами (`сто долларов`, `two hundred dollars`), или
MVP держится только на цифрах?

**Почему именно сейчас.** Вы только что ввели рамку MVP — и внутри вашего же списка триггеров есть
вид записи, который стоит на порядок дороже остальных:

| Вид записи | Стоимость | Почему |
| --- | --- | --- |
| `$12.50`, `12,50 €` | минимальная | символ и цифры: таблица символов плюс регулярка |
| `5 млн ₽`, `1.2M$` | низкая | цифры плюс таблица множителей: тыс., млн, млрд, K, M, B |
| `сто долларов` | высокая | словарь числительных на два языка со склонениями: «двести тридцать пять долларов», «two hundred and thirty-five dollars», «полторы тысячи» |

Числа словами — это не регулярка, а грамматика двух языков. В MVP это обычно самая дорогая часть
при самой низкой отдаче: на реальных страницах суммы почти всегда записаны цифрами.

**Рекомендую:** в MVP только цифры, включая множители `млн`/`тыс`/`K`/`M`. Числа словами — за
рамкой MVP. Множители почти бесплатны и дают большую часть выигрыша; слова — наоборот.

**Честная цена решения:** новостные тексты пишут «два миллиона рублей» словами, и именно этот
случай останется непокрытым.

**Ваш ответ.** В MVP входят все цифровые записи вместе с множителями. Числа словами — нет.
Множители дорогой частью не считаем: они известны и используются повсеместно.

**Уточнение термина.** `Spelled numeral` убран из `CONTEXT.md` по тому же правилу, что и `Range`.

## Раунд 5. Какие обозначения валют признаём

## Раунд 6. Форматы чисел

**Вопрос.** Как читать разделители, когда запись неоднозначна?

**Почему это сейчас.** Языка два, страниц — миллион, и одна и та же запись читается по-разному:

| Запись | В английском соглашении | В русском/немецком |
| --- | --- | --- |
| `1,234.56` | 1234.56 | — |
| `1.234,56` | — | 1234.56 |
| `1 234,56` | — | 1234.56 |
| `1.234` | 1.234 | 1234 |

Ошибка здесь не косметическая: цена умножается на 1000, и человек этого не заметит.

**Рекомендую** правило без угадывания по языку страницы:

1. Есть оба разделителя (`,` и `.`) — десятичный тот, что правее.
2. Один разделитель, после него ровно три цифры, а перед ним 1–3 цифры — это разделитель тысяч.
3. Один разделитель в остальных случаях — десятичный.
4. Пробел, включая неразрывный, между группами цифр — разделитель тысяч.
5. Всё остальное — не срабатывание.

Пункт 2 — сознательный компромисс: `$1.234` прочтётся как 1234. Три знака после запятой в деньгах
почти не встречаются, а тысячи через точку — встречаются. Ошибка в редком случае дешевле, чем
неверный порядок величины в частом.

Альтернатива: выбирать соглашение по валюте (USD — точка десятичная, RUB/EUR — наоборот). Проще
на вид и ломается ровно там, где страница смешивает соглашения.

**Ваш ответ.** Правило простое и без исключений: десятичный разделитель — самый правый из `,` и `.`;
если он один — он десятичный; пробел (включая неразрывный) между группами цифр — тысячный.

- `1,234.56` → 1234.56
- `1.234,56` → 1234.56
- `1 234,56` → 1234.56
- `1.234` → 1.234

**Проверка на вашем же языке — правило не выдерживает.** В русском тысячи разделяются точкой или
пробелом. Значит запись `1.234 ₽` на русской странице — это 1234 ₽. По вашему правилу она
прочтётся как **1.234 рубля**, то есть один рубль двадцать три копейки. То же с английской
записью `$1,234`: по правилу это 1.234 доллара вместо 1234.

То есть «всегда десятичный» не спасает от ошибки в 1000 раз, а переносит её на самую массовую
запись тысяч в обоих целевых языках: в русском — точка, в английском — запятая. Обойтись без
выбора нельзя: `1.234` одновременно означает и «одна целая 234 тысячных», и «тысяча двести
тридцать четыре». Правило должно сказать, какую из двух трактовок считать основной.

**Рекомендую:** единственный оставшийся источник информации на этот вопрос — само обозначение
валюты. Оно у нас всегда есть, потому что без него нет срабатывания, и это не угадывание по
языку страницы:

| Пара | Соглашение | Что значит `1.234` | Что значит `1,234` |
| --- | --- | --- | --- |
| `$`, `£`, `¥`, JPY | английское: запятая — тысячи | 1.234 | 1234 |
| `€`, `₽`, RUB, EUR | европейское: точка — тысячи | 1234 | 1.234 |

При этом оба правила продолжают работать без изменений (оба разделителя, пробел), а
двусмысленность решается только там, где она реально есть. Стоимость — таблица из пяти строк.

Альтернатива — асимметричное правило без таблицы: «три цифры после разделителя — тысячи, если это
запятая, и десятые доли, если точка». Тогда `$1,234` = 1234 (верно), но `€1.234` = 1.234 (ошибка
в 1000 раз на европейской странице). То есть баг просто переезжает из английского в европейский.

**Ваш ответ.** Валюту делаем арбитром, таблица принята:

| Пара | Соглашение | `1.234` | `1,234` |
| --- | --- | --- | --- |
| `$`, `£`, `¥`, JPY | запятая — тысячи | 1.234 | 1234 |
| `€`, `₽`, RUB, EUR | точка — тысячи | 1234 | 1.234 |

Полный набор правил чтения числа, в порядке применения:

1. Есть оба разделителя — десятичный тот, что правее; валютная таблица не участвует.
2. Пробел или неразрывный пробел между группами цифр — разделитель тысяч.
3. Один разделитель — решает обозначение валюты по таблице.
4. Разделителей нет — целое число.
5. Всё остальное — не срабатывание.

Термин `Number convention` добавлен в `CONTEXT.md`; словом `locale` этот механизм больше не
называем — он не про язык страницы.

**Правка 2026-11-08 (Р2).** Валютная таблица снята решением пользователя: «счёт цифр». Действующее
правило — часть I, раздел 12.2. История решения стоит трёх строк: счёт цифр был моей первой
рекомендацией этого раунда; вы выбрали «всегда десятичный», после проверки на `1.234 ₽` — таблицу по
валюте, и теперь вернулись к счёту цифр, уже зная цену обоих отходов от него.

## Раунд 7. Где оверлей не должен появляться

**Вопрос.** Глушим ли срабатывание в техническом тексте, в полях ввода и на «чужих» символах
доллара — или показываем оверлей буквально везде?

**Почему это сейчас.** Разборщик почти описан, и последний его пункт — не «что распознавать», а

| Где | Пример | Что произойдёт без гейта |

3. Выделение внутри `input`, `textarea`, `[contenteditable]` — оверлея нет в MVP.

выделения, и позиционировать оверлей не от чего. Это лучше знать до вёрстки, а не после.

**Ваш ответ.** Оверлей работает всегда, но срабатывает только когда в выделении нет ничего, кроме

Пробелы по краям и внутри числа не мешают. Принцип, который человек должен усвоить: хочешь

**Что это правило сделало с моими тремя гейтами:**

- **Гейт 1 (буква слева от `$`) — растворён.** `C$12` целиком содержит букву, значит это уже не

- **Гейт 3 (поля ввода) — не решается правилом вообще.** Это не про содержимое выделения, а про
  то, что внутри `input` и `textarea` браузер не отдаёт прямоугольник выделения — оверлей не к

**Термин.** `Exact selection` добавлен в `CONTEXT.md`: выделение, содержимое которого без пробелов —

## Раунд 8. Насколько «актуальный» курс

**Вопрос.** Какая свежесть курса нужна: дневного справочного достаточно, и можно ли переиспользовать
один полученный курс для нескольких выделений внутри окна свежести?

**Почему сначала свежесть, а не провайдер.** Провайдер — следствие. Если нужны минуты, бесплатных
вариантов без ключа нет и появляется ключ в бандле. Если достаточно дня — есть вариант без ключа и
без квот.

**Что я проверил по документации Frankfurter v2 (на сегодня):**

| Факт | Значение |
| --- | --- |
| Ключ | не нужен |
| Цена | бесплатно, включая коммерческое использование (смешанные курсы) |
| Свежесть | раз в день, справочный mid-market курс |
| Валюты | 239, включая `RUB` |
| Квоты | суточных и месячных лимитов нет, только анти-абьюз-лимит |
| Конвертация | эндпоинта нет: берём `rate` и умножаем сами |

Бесплатных провайдеров с дневной свежестью несколько (Frankfurter, ExchangeRate-API open access);
с минутной свежестью — только с ключом.

**Где мы противоречим сами себе.** В `CONTEXT.md` записано: «курс никогда не сохраняется для
последующего использования». Но при автопоказе каждое выделение — это запрос, и на странице магазина
их будут десятки. Значит либо запись в глоссарии слишком сильная, либо мы осознанно отказываемся от
кеша.

**Рекомендую:**

1. **Свежесть** — дневной справочный курс. Для вопроса «сколько это в рублях» минутная точность
   ничего не меняет.
2. **Провайдер** — Frankfurter v2, запрос из service worker: там он идёт в обход CORS по
   `host_permissions`, выданному только на `api.frankfurter.dev`, и страница не видит наших запросов.
3. **Кеш** — один курс на пару валют с окном свежести (предлагаю 6 часов). Запрос всё равно
   обязателен: без сети оверлея нет. Кеш здесь не «офлайн», а «не спрашивать одно и то же дважды
   за минуту».
4. **Формулировку в глоссарии** меняю на: курс никогда не выдумывается, но может быть переиспользован
   внутри своего окна свежести.

Альтернатива: без кеша вообще, запрос на каждое выделение. Модель проще, трафик больше, и активное
использование упирается в анти-абьюз-лимит провайдера.

**Ваш ответ.** Свежесть — не сутки, а 4–6 часов. Запрос делается только тогда, когда выделение
совпало и для пары нет курса в окне; потом курс лежит в кеше и повторных запросов нет.

**Про «горячий кэш» — терминология.** Строго говоря, «горячий» описывает попадания, а не
устройство: кэш горячий, пока в него продолжают попадать запросы. У нас другое: кэш **по паре
валют с окном свежести**. Он будет горячим ровно настолько, насколько человек выделяет суммы в
одной и той же паре; для редкой пары это холодный кэш с одним попаданием на 6 часов.

**Следствие для реализации, которое лучше знать сейчас.** В MV3 service worker умирает через
~30 секунд простоя. Кэш в памяти не переживёт даже переключения вкладки, и «окно 4–6 часов»
превратится в «окно до следующего засыпания воркера». Кэш должен лежать в `storage.local` вместе с
именем времени получения.

**Поправка к моей же формулировке.** Окно свежести управляет частотой запросов, а не возрастом
числа. Провайдер публикует справочный курс раз в день (ЕЦБ — около 16:00 CET), поэтому и при окне
4 часа, и при окне 6 часов человек может увидеть вчерашний курс. Это свойство провайдера, а не
кеша: без кеша он увидит тот же вчерашний курс, только запросит его чаще.

**Принимаю:** окно 6 часов — верх вашей вилки. При дневном провайдере 4 и 6 часов неразличимы по
точности, а 6 — вдвое меньше запросов. Хотите жёстче — это одна константа.

**Термины.** В `CONTEXT.md`: `Rate` теперь «никогда не выдумывается, но переиспользуется внутри
своего окна свежести»; появились `Pair` и `Freshness window`.

## Раунд 8б. Что видно, пока курса нет

**Вопрос.** Что показывает оверлей во время запроса и что — если сеть не ответила?

**Почему это сейчас и почему это следствие вашего же правила.** Выделение срабатывает моментально, а

| Момент | Варианты |
| --- | --- |

## Раунд 9. Чем собирать два браузера

## Раунд 10. Где стоит оверлей

**Вопрос.** Оверлей появляется над выделением или под ним, и что он делает у края окна?

**Почему это сейчас.** Это последняя деталь интерфейса, без которой нельзя сказать, мешает виджет
или нет. Человек выделяет сумму — если окно закрывает собой соседнюю строку с ценой, продукт
раздражает сильнее, чем помогает.

**Рекомендую:**

1. По умолчанию — **под** выделением. Порядок чтения: сначала сумма, потом результат; окно не
   закрывает то, что человек только что прочитал.
2. Не влезает снизу — **переворачиваем вверх**. Не влезает ни там, ни там — прижимаем внутрь окна
   по вертикали.
3. По горизонтали — по левому краю выделения; при выходе за правый край сдвигаем внутрь.
4. Привязка — к **последнему** прямоугольнику выделения (там, где заканчивается взгляд), а не к
   первому.
5. При прокрутке — пересчитываем позицию, а не прячем: выделение при прокрутке никуда не девается,
   и исчезающее окно читается как глюк.

**Что здесь решается не голосованием, а платформой** (привожу, чтобы не открывать заново):

| Решение | Причина |
| --- | --- |
| Хост-элемент вешаем на `document.body`, а не внутрь абзаца | иначе `overflow: hidden` предка обрежет окно |
| `position: fixed` и координаты из `getBoundingClientRect()` | координаты уже в системе окна, не нужно складывать со скроллом |
| `z-index` по максимуму | иначе чужие панели окажутся выше |
| Внутри `ShadowRoot` — `all: initial` на корне | иначе наследуемые свойства страницы протекут внутрь |

**Чего сознательно не делаем:** не отступаем, если сайт рисует свою панель над выделением (Medium,
Notion). Это редкие сайты, а «уступить» потребует знать чужие панели по именам.

**Ваш ответ.** В окне только результат конвертации: исходная сумма уже видна в тексте. Окно
появляется рядом с выделением и не накладывается на него, занимая свободное место сверху или снизу —
там, где его больше. Прокрутка или снятое выделение закрывают окно; клик вне — тоже. Отступ до
выделения — настройка, по умолчанию 4px.

**Что поменялось против моей рекомендации:**

| Было | Стало |
| --- | --- |
| по умолчанию снизу, переворот только если не влезает | сторона выбирается по объёму свободного места |
| при прокрутке пересчитывать позицию | при прокрутке закрывать |
| исходная сумма плюс результат | только результат |

**Дыра в правиле «где больше места» — закрыта вашим решением: при равенстве сверху.** Точная
формулировка: если свободное место сверху и снизу различается меньше чем на высоту самого окна,
выбираем **верхнюю** сторону.

**И вы правы, моя рекомендация была хуже.** Я предлагал низ, исходя из «порядка чтения»: сначала
сумма, потом результат. Аргумент работает в другую сторону. Чтение идёт сверху вниз, поэтому окно
сверху закрывает уже прочитанный текст, а окно снизу — тот, который человек ещё не читал. Для
временного окна первое безвредно, второе — нет. Заодно это совпадает с привычкой панелей выделения
(Medium, Notion), которые тоже появляются сверху.

**Про клик по окну, вы это спросили.** В MVP — ничего не делать. Тогда окно остаётся чистым
дисплеем, и это честно: чтение — не действие, и человек не должен бояться случайно что-то
нажать. Очевидное расширение на потом — клик копирует результат в буфер: человек, выделивший цену,
часто хочет вставить её дальше. Но это превращает дисплей в инструмент: нужен отзыв «скопировано»,
обработка отсутствия прав на буфер, отмена. В MVP не берём.

**Следствие решения «только результат».** Число без валюты бесполезно, поэтому обозначение целевой

вторая сумма, а подпись: без неё человек не отличит свежий курс от вчерашнего.

**Термины.** В `CONTEXT.md`: `Result` — единственное число в окне; `Overlay` дополнен словами «только
результат, никогда исходная сумма».

**Поправка по сцене.** Пример один и тот же для всех и **не переводится**. Меняются только пояснения

| Слой | Что там |
| --- | --- |

не понял, зачем она нужна.

## Раунд 12. Язык и формат вывода

**Проблема первая — механизм.** Платформенный способ — `_locales` и `chrome.i18n.getMessage` — берёт

| Вход | Выход |
| --- | --- |

## Раунд 14. Где живут настройки

**Вопрос.** `storage.sync` или `storage.local`?

**Почему это развилка, а не мелочь.** Настроек мало: язык, тема, валюта, отступ. Синхронизация значит,
что человек поставил расширение на ноутбук и на рабочий компьютер, и вторая установка уже знает его
валюту и язык. Локальное хранилище значит, что каждая установка знакомится заново — вместе с
онбордингом.

**Рекомендую `storage.sync` для настроек.** Набор крошечный (лимит `sync` — 100 КБ, у нас сотни
байт), а валюту человек выбирает про себя, а не про устройство. Тогда онбординг показывается только
там, где настроек ещё нет.

**Курсы остаются в `storage.local`** — это не настройка, а кэш; синхронизировать чужие числа между
устройствами бессмысленно.

**Ваш ответ.** Если есть возможность — настройки синхронизируемые.

**Принято: `storage.sync` для настроек, `storage.local` для курсов.** Пять значений: язык, тема, тема
оверлея, целевая валюта, отступ.

**Что это даёт.** Поставил на втором браузере или втором компьютере — настройки уже там, и онбординг
не показывается вовсе. Онбординг живёт только там, где настроек нет.

**Три вещи, которые всплывут при реализации:**

1. **Квота на запись.** У `storage.sync` лимит не только на объём (100 КБ, у нас сотни байт), но и на
   частоту: 1800 записей в час и 120 в минуту. Ползунок отступа при перетаскивании даёт десятки
   изменений в секунду и упрётся в этот лимит. Значит отступ пишется по отпусканию ползунка или с
   задержкой в несколько сотен миллисекунд, а не на каждое движение.
2. **Асинхронность и мигание онбординга.** Решение «показывать онбординг или нет» принимается после
   чтения хранилища, а чтение асинхронное. Если нарисовать интерфейс раньше, человек увидит онбординг,
   который тут же сменится настройками. Значит: сначала читаем, потом рисуем.
3. **Синхронизация доступна не всем.** Если человек не вошёл в аккаунт браузера, `storage.sync` работает
   как локальное хранилище. Это не ошибка и не повод для сообщений — просто данные не поедут на другое
   устройство.

## Раунд 5а. Слова-валюты — возврат к отложенному

**Почему сейчас.** Пункт висел с раунда 5: тогда вы ответили про символы и ISO-коды, а про слова
ответа не было, и я записал его как нерешённый, а не как «нет». Теперь всё остальное закрыто, и это
последняя крупная развилка парсера.

**Вопрос.** Признаём ли слова-валюты: `100 рублей`, `50 долларов`, `20 евро`, `100 yen`?

**За.** В русском тексте деньги чаще всего пишут именно так. Сейчас `100 рублей` для нас — не сумма, а
просто текст, и человек не получит ничего. То есть самая частая форма записи денег в главном для нас
языке не работает.

**Против.** Слова требуют морфологии (`рубль`, `рубля`, `рублей`) и несут неоднозначность: `фунт` —
это и вес, и валюта; `крона` — пять разных стран; `доллар` — не только американский.

**Рекомендую: да, но по закрытому списку.**

| Слово | Корень для поиска | Валюта |
| --- | --- | --- |
| рубль, рубля, рублей | `рубл` | RUB |
| доллар, доллара, долларов | `доллар` | USD |
| евро | `евро` | EUR |
| иена, иены | `иен` | JPY |
| dollar(s), euro(s), yen, ruble(s) | те же слова | те же валюты |

**Выбрасываем сознательно:** `фунт` (вес), `крона` (какая?), `франк` (какой?), `гривна`/`тенге` и
прочие — их можно добавить потом одной строкой в таблицу.

**Почему `доллар` = USD — не догадка.** Вы уже решили, что `$` — это всегда USD, без угадывания по
языку страницы. Слово `доллар` ведёт себя так же, как знак `$`: одно значение, без вариантов. Иначе
придётся объяснять, почему знак — USD, а слово — неизвестно что.

**Цена.** Парсер получает вторую форму индикатора: не точное совпадение, а корень плюс окончания. Это
усложняет одну функцию и одну её таблицу тестов, и ничего больше.

**Ваш ответ.** Слова-валюты в MVP не входят.

**Принято: отказ, но не навсегда.** `100 рублей` остаётся для парсера просто текстом. Записано как
решение, а не как «забыли».

**Что это значит на практике, без сглаживания:** человек, выделивший `100 рублей` в русской статье,
не получит ничего. Это будет ощущаться как «расширение не работает» именно на том языке, для которого
мы делаем интерфейс. Цена настоящая.

**Почему такая цена приемлема:** рядом почти всегда есть форма, которую мы понимаем — `100 ₽` или
`100 RUB`. А для сумм вообще без обозначения есть ручной конвертер в попапе.

**Как вернуть, когда надоест:** добавить строку в таблицу корней и тест к ней. Архитектуры это не
задевает — мы проверили это самим отказом.
